# 学习实践路线：围绕上下文与真实效果

## 学习契约

目标不是“让模型连着调用几次工具”，而是你能回答并动手验证：

- 本轮模型输入由哪些稳定规则、任务、运行状态、历史与工具信息组成？
- 哪些数据是原始事实，哪些是派生视图，哪些是会丢信息的总结？
- 为什么本轮选择这些文件／片段？移出后怎么恢复？
- 输入预算包含 schema、结构开销、动态消息和输出预留吗？
- 一次失败属于模型、检索、上下文、工具、验证还是停止规则？
- 策略改善是否在同模型、同任务、同预算下经过重复实验，而非单次演示？

建议每阶段 1–3 次练习，每次 60–90 分钟；按理解与验收推进，不按日历赶进度。这里的时长只是学习安排建议。

## 阶段 1：最小闭环与协议（现在可以开始）

读 src/types.ts → protocol.ts → runner.ts → providers.ts。不先读 UI 或插件系统。

操作：npm run demo，逐步看 list_files、read_file、propose_edit、run_tests 和 final。批准提案前检查 sum.mjs 未改变，批准后查看实际文件，测试通过后核对 tool_result。

练习：让一次回复 JSON 无效；让工具名为不存在的 bash；让动作连续重复三次；让模型没有跑测试就 final。

验收：能画出“请求持久化 → 模型响应验证 → 动作持久化 → 门禁 → 工具结果 → 下一请求”，能区分模型 final 与 harness 的验证标签。没有通过测试时绝不能将 model final 当成功。

注意：第一版使用文本 JSON 动作协议，不是 OpenAI 原生 function calling。目的是先看清状态机，后面再换传输协议。

## 阶段 2：完整历史与可见上下文

读 src/session.ts 和 context.ts 的 historyUnits。对照 reference/architecture.md:132–138 与官方 session 文档。

操作：打开会话 events.jsonl，定位 config、request、assistant、tool_result、proposal、approval、note、stop。request 保存那一轮实际 messages 和选择指标；上下文裁剪不重写旧事件。

练习：写一个只读事件时间线；重开 Session 比较事件；截断一行测试拒绝继续；模拟 assistant 已记录但工具结果缺失，解释为什么不能自动再执行编辑。

验收：能从日志找回某一次请求，能解释“重建记录”不等于“重放副作用”。第一版对崩溃中断选择 fail closed，不提供 exactly-once 保证。

## 阶段 3：预算与最小有效上下文

读 src/context.ts；执行 npm run experiment。

当前策略：

- full：所有完整动作单元，无裁剪；超预算报错，用作基线。
- tail：裁剪大工具结果，只保留近期成对单元；可能失去早期事实。
- checkpoint：和 tail 相同，再加入模型保存的短笔记；原始历史仍可按 seq 恢复。

预算原则：总窗口扣除输出预留与安全余量才是输入上限。稳定规则、工具定义、任务、动态请求号和 checkpoint 都计入粗估。当前估计不是精确 tokenizer，不是账单。

练习：调整 window、recentUnits、toolResultChars；加入中文、JSON schema 与 emoji；用很大的当前任务和最新单元触发不可压缩错误；故意切开调用／结果，观察拒绝。

验收：所有已成功编译请求的 selectedTokens 不超过 inputLimit；最新完整单元与系统规则不被静默丢弃；每个省略段有原始 seq；能解释减少 token 不必然提高成功率。

改进作业：把“全历史先裁剪”改成按年龄／工具类型裁剪，额外保留最近的验证错误；比较其信号是否更好，而不是只比字数。

## 阶段 4：checkpoint 与信息损失

读 save_note、history_search、history_read。对照官方 compaction 文档；本项目不是官方摘要后端的等价实现。

先定义短结构：目标／不可变约束／已改文件及 hash／验证证据 seq／失败与排除假设／剩余步骤。来源 seq 必须能回链，过期状态必须重验。

练习：在第 1 步保存重要 API 约束，加入 10 次长工具结果，再让模型继续；对照无笔记、正确笔记、漏约束笔记、错误／过时笔记。让一个关键细节只在原历史里，模型必须 history_search + history_read 恢复后才能解决。

验收：在实际模型输入和最终独立测试两个层面检查保真。标记存在只证明上下文管道，不证明模型遵循。记录丢失字段、错误摘要与恢复次数。

当前实现只在历史已被移出时注入最近 8 条笔记。旧笔记仍在原日志；没有跨会话长期记忆、自动写笔记或 rollover 事务。

## 阶段 5：实现真正的压缩后端（下一阶段作业，未实现）

不要把“请求前把所有历史总结一下”当完整方案。先定义 CompressionEngine 边界，再实现可替换后端。

建议状态：prepare → 选择安全成对范围 → 记录 compaction/start → 生成候选摘要 → 校验保真与缩减 → 记录摘要／来源和替换事件 → compaction/end。压缩应在工具批次结束的安全点，不在审批中或缺结果时发生。

练习：先写确定性结构 checkpoint，然后加模型摘要；摘要为空、变长、字段缺失、取消、半途崩溃、原历史变化均需测试。失败时保留旧视图，不能宣称压缩成功；若发生部分持久化，先定义可检测状态再谈恢复。

验收：系统规则与当前任务不进入有损摘要；旧原文能追溯；摘要成功和失败都有来源与观测点；相同日志的 detached 读取得到相同可见历史。

官方参考：compaction-basic 的 index.ts 只显示路由和调用关系；本次没有完整读 region.ts／summarizer.ts，不能声称已经审计官方压缩事务实现。用 scripts/fetch-reference.mjs 扩展下载范围后再读 callee。

## 阶段 6：检索与前缀稳定

学习顺序：文件列表 → 精确字符串检索 → 定向分段读取 → 项目指令文件按需加载 → 可选符号索引。暂不引入 embeddings，先明确每一步的信息增益。

练习：把几百行无关文件与真正修复点混在一起；对照全文件灌入与“先检索再读”。给文件片段添加 path、行号、hash 和来源 seq，编辑前验证 hash。

前缀实验：工具 schema 和稳定规则留在头部，时间／cwd／请求号等动态状态在尾部。本项目只记录 prefixHash，**没有测缓存命中**。正式 API 后用提供方 reported cache usage 测量，不能从 hash 不变推断命中。

验收：命中率、关键片段召回率、实际输入量、重读次数、成功率一起看。工具结果是非可信数据，检索到的指令不能提升权限。

## 阶段 7：效果优化要有证据

现有 npm run eval 是 plumbing smoke，不是能力基准。在线命令见接入说明。当前小套件只用于确认接入和记录指标。

建立至少 10–20 个独立任务：单文件 bug、跨文件修复、API 兼容、错误测试定位、长程约束、多轮用户纠偏、旧历史恢复、输出截断、相似文件干扰、权限拒绝。为每个任务固定仓库起点与不由 Agent 控制的独立验收测试；不能只凭 Agent 自己写的测试。

每个策略固定同一模型、模型参数、动作／时长／费用预算，至少重复 3 次。尽可能交错实验顺序，记录温度与版本、时间、模型路由和任务版本。Trae 手动通路额外记载人为搬运错误与隐含上下文，结果不和正式 API 直接混表。

优先指标：

1. 独立验收通过率，保留失败和未验证，不排除坏例。
2. 约束遵守／摘要保真／关键证据恢复率。
3. 工具错误、无进展轮数、重复动作、修复轮数。
4. API reported input／output／cache tokens 与耗时；未知是 null，不是零。
5. 每成功任务成本以及预算超限率。

消融顺序：A full 基线 → B 只裁剪大工具结果 → C 近期单元选择 → D 加 checkpoint → E 加恢复提示 → F 检索／验证／重试。每次只变一个因素。当前脚本的 tail 同时改变裁剪和历史选择，**不能归因到单一机制**；请先加 prune-only 策略作为作业。

失败分类模板：任务／策略／模型／输入来源／丢失约束／工具失败／最终 diff／独立测试／是否修复／根因证据 seq。先找主要失败桶，再做优化，避免“更长 system prompt”“加多个 Agent”等无证据措施。

## 阶段 8：把学习版推进到实用版

按实际失败顺序加能力：原生 tool_calls 和 streaming → 取消／超时 → 幂等工具与事务式修改 → 真 OS 沙箱与网络隔离 → 多文件编辑与 git diff → 长程 checkpoint／自动摘要 → 多 Agent（仅在隔离上下文确有收益时）。

多 Agent 作业先只比较一个只读子 Agent：给它最小任务、边界与产物格式，父 Agent 只接收可追溯摘要及证据。评测收益要扣除调度与上下文成本。不默认“多 Agent 比单 Agent 强”。

最后再映射到 Cordis 插件：ModelProvider → LLM adapter；Tools → tool registry；上下文注入 → pre-step／session events；CompressionEngine → compaction seam。不要先复刻完整插件框架，把精力耗在 UI 和依赖系统上。
